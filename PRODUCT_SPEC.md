# PearTV Launcher — Product & Technical Specification

**Target device:** NVIDIA Shield TV Pro (Tegra X1+, 3GB RAM, Android 11 — confirmed via `adb shell getprop ro.build.version.sdk`/`ro.build.version.release` (API 30) on the actual reference unit; this model's final OS update ships that ceiling, so API 30 is a hard floor *and* ceiling for it, not just a current version)
**Mission:** A custom Android TV home launcher that matches tvOS-grade input latency, spring-physics micro-interactions, and visual polish — with zero D-pad focus lag.
**Status:** Phase 3 (device-verified feature build-out) in progress — see the closing status note at the end of this document for exactly what's built/confirmed vs. still open.
**Reference source:** Visual layout hierarchy and app/provider metadata cross-referenced from the `../hamtv` web prototype (UI/UX and data reference only — no CSS, JavaScript, or DOM focus/animation logic ported; see §3.1.1, §3.2.1, §3.3.1). All motion remains governed exclusively by §1 (Compose `graphicsLayer` + spring physics). **Second reference source (added after Phase 2 device testing):** actual Apple tvOS photos in `design/` (gitignored, local-only — not committed) — used to correct several `hamtv`-derived assumptions that don't match real tvOS behavior; see the "tvOS Photo Reference" callouts in §1.4, §3.1.1, and §4. **Third reference source (added Phase 3, most authoritative of the three):** Apple's own documented Top Shelf template system (user-supplied written description of the official behavior, not a screenshot) — see §3.1.2, which supersedes the `hamtv`/photo references wherever they conflict with it. **Fourth reference source (added Phase 3, broadest in scope):** Apple's official tvOS Human Interface Guidelines, compared feature-by-feature against the current build rather than against just the Top Shelf — see §5, items 7–13.

## Decisions Log

Locked decisions from Phase 2 kickoff review, superseding the corresponding items originally raised as open questions in §5.

| Decision | Choice | Rationale |
|---|---|---|
| Min supported API level | **API 30 (Android 11), strict baseline** | Shield Experience 9.2+ ships Android 11. No back-compat shims for anything below API 30. |
| Grid tile aspect ratio | **16:9 (1.78:1), matching the native 320×180 leanback banner** | Forcing the `hamtv` reference's 1.54:1 ratio would require dynamic cropping/letterboxing on every third-party app's system-supplied banner. Standardize the general grid on native 16:9; the curated enrichment schema (§3.2.1: `logoFit`/`logoPadding`) remains the escape hatch for custom tiles that need different framing. |
| Ambient background wash technique | **Dual-stop radial gradient, tinted with `accentColor`, no real-time blur** | `RenderEffect` hardware blur requires API 31+; API 30 is the confirmed floor. A real-time 120px Gaussian blur on API 30 has no cheap RenderThread path and would violate the §0 frame budget. A radial gradient reproduces the tvOS ambient-lighting feel without a blur compositing cost. |
| Lazy grid/row + focus-group APIs | **Plain `androidx.compose.foundation.lazy`/`lazy.grid` (`LazyRow`, `LazyVerticalGrid`, `GridCells`) + `Modifier.focusRestorer()`, not `androidx.tv:tv-foundation`** | Phase 1's draft assumed `androidx.tv:tv-foundation` shipped `TvLazyRow`/`TvLazyVerticalGrid`/`Modifier.focusGroup()`. Verified against the actual resolved 1.0.0 artifact during Phase 2 build verification (§1.3, §2.2 build note): none of those exist in the stable release — that alpha-era API surface was dropped once equivalent D-pad focus-scroll support landed in mainline Compose Foundation. `tv-foundation` was removed from `app/build.gradle.kts` as a result; only `tv-material` is still a dependency. |
| Tile art rendering | **`ContentScale.Crop` remains the generic default; curated apps get a hand-tuned `Fit` + padding + solid `accentColor` "logo card" via the enrichment schema (§3.2.1)** | tvOS photo reference (`design/`) shows every real tvOS icon as a compact, centered logo/wordmark on a flat color card with generous padding — not edge-to-edge banner art. Crop is still the right *fallback* for arbitrary system banners we have no curated art for (guarantees no letterbox gap regardless of source aspect, §3.1.1); it just shouldn't be the *only* treatment available. |
| Hero name/tagline text | **Removed. Replaced by a per-tile focus label (§1.4)** | tvOS photo reference shows the focused icon growing a text caption *below the tile itself* on focus, not a separate hero text block elsewhere on screen. `HeroBanner`'s name/tagline/subtitle text (originally extracted from `hamtv`, a web project with no per-tile focus concept) is redundant once every tile carries its own label. |
| Rich per-app content source | **Three-tier hybrid: real Channels data (Tier 3) > curated TMDB backdrop art (Tier 1) > system banner (Tier 2)** | Originally reasoned from an `adb shell content query` against `content://android.media.tv/{channel,preview_program,watch_next_program}` returning zero rows for every installed app, taken at the time as "nothing currently publishes to Channels." **That premise was wrong, corrected during Task #20's implementation**: `adb shell`'s own calling identity (the shell UID) isn't granted `READ_TV_LISTINGS` and — as later discovered — `TvProvider` also rejects any `selection`/WHERE clause on the Channels table outright (`SecurityException: Selection not allowed`), so every earlier `content query` attempt (shell-run, always with an implicit or explicit selection) was silently denied, not genuinely empty. Once queried correctly *from the app itself* (unfiltered query + client-side `package_name` filtering, `READ_TV_LISTINGS` actually granted), **five installed apps on the reference device turned out to already publish real channels**: Plex, Hulu, Jellyfin, Dolphin Emulator, and Apple TV. Tier 3 is the *common* case on this hardware, not the rare exception the original finding assumed — though the three-tier fallback structure itself remains correct and necessary, since Tier 3 still isn't universal (BrowseHere/Daijishō/RetroArch/etc. publish nothing). **Tier 1** (curated apps, §3.2.1's `tmdb_provider_id`) fetches TMDB backdrop *art only* when Tier 3 isn't present for that app. **Tier 2** (default fallback) — the existing system-banner + accent-wash treatment. **Tier 3** (highest display priority when present) — a focused app's own real Channels data replaces the hero with Content Rows (§3.1.1) entirely. |
| Theme | **Explicit in-app dark/light toggle, not system-follow** | tvOS photo reference is a light-mode capture; our build has been dark-mode only. Reverses §4's original "no user-customizable themes" non-goal — see that section for the updated scope note. Requires at minimum a settings entry point, which didn't exist before this decision (see §4). |
| Status bar | **Add a clock, top-right, always visible — no profile/account avatar** | tvOS reference shows a clock + profile avatar; we have no accounts/profile concept to justify an avatar, so clock-only. This was already documented as extracted-but-unbuilt in §3.1.1's `hamtv` reference; this decision confirms it's an actual Phase 3 build item now. |
| Icon fallback (generic default icon) | **Leave as-is — render whatever `PackageManager` returns, no detection of the generic system default icon** | The tile-level initial-letter fallback stays a decode-failure-only defensive path, not something actively triggered for apps that simply declare no custom icon. Matches how every other Android TV launcher behaves; detecting "is this the generic default drawable specifically" would add real complexity for a genuinely rare case. |
| Baseline Profile generation environment | **On-device (the actual Shield TV Pro), not emulator/CI** | We already have a working, direct ADB connection to the reference hardware, used for all testing this project has done — no new infrastructure needed, and it's more representative of real dex2oat/ART behavior than an emulator would be. No CI pipeline exists for this project to make the emulator route worthwhile. |
| Per-tile focus label reserved space | **Reserved permanently (occupied whether or not the tile is focused; only the label's own alpha animates)** | Resolves §1.4's own "unresolved detail" — a conditionally-present label would reflow every neighboring row/tile on each focus change. Reserved space avoids that layout thrash entirely. Confirmed on-device this also requires explicitly requesting the whole tile-plus-label area into view on focus (`BringIntoViewRequester` around both, not just the focusable tile) — Compose's default scroll-into-view only considers the focusable node's own bounds, which left the label clipped off-screen for any tile focused near the viewport edge. |
| Hero region vs. app grid vertical split | **`Column` weights (`HeroSectionWeight`/`AppGridWeight`, currently 1f/1f), not a fixed dp height** | The original `HeroSectionHeight = 480.dp` (already flagged in this doc as "a first concrete value; not yet the final re-derived percentage") was confirmed broken on the actual Shield during §1.4 on-device testing: its screen reports a 960x540dp logical size (1920x1080 physical @ 2.0 density), so a fixed 480dp consumed 89% of total height, leaving only 60dp for the *entire* scrollable app grid (confirmed via `adb shell uiautomator dump`: the grid's own accessibility-tree bounds were a 60dp-tall sliver, clipping every row before this fix). Weight-based split scales with whatever height is actually available rather than assuming this one device's dp height. |
| Curated metadata enrichment schema (§3.2.1) storage | **Bundled JSON asset (`assets/app_enrichment.json`), loaded once into an in-memory `Map<String, AppEnrichment>` — not Room** | Matches the schema's own description ("local JSON or Room table, bundled + user-editable") at the low end of that range: a handful of curated provider rows doesn't justify a database's migration/query ceremony. Seeded directly from §3.3.1's provider table (`accentColor`, `tmdbProviderId`, keyed by the same unverified-but-harmless package names — a non-matching package name is simply a no-op lookup, not a launch-target risk, since actual launching still goes through `PackageManager`'s leanback query unconditionally). `displayName`/`pinnedToTopShelf` fields exist in the schema but weren't seeded with real curation calls yet — no source of truth for "which specific apps deserve a permanent tray slot" existed to draw from, so the existing fallback (first N alphabetically) was left alone rather than guessed at. |
| Tier 1 TMDB content model | **TMDB Discover API (`/discover/movie`, `with_watch_providers`/`watch_region=US`/`sort_by=popularity.desc`), top result's backdrop only — movies only for v1** | TMDB has no "artwork for streaming provider X" endpoint (`tmdb_provider_id` identifies a *service*, not a title). Discover's most-popular-on-that-provider result stands in for the provider with real, current TMDB art rather than a specific diegetic claim about one title. Confirmed live end-to-end on-device (real API key, real network call) — Apple TV and Hulu each render a distinct, real TMDB backdrop; apps without a curated `tmdb_provider_id` (e.g. Daijishō) correctly keep falling back to Tier 2. A combined movie+TV query is a noted follow-up, not a v1 correctness requirement. |
| TMDB fetch networking | **Plain `OkHttpClient` (shared with Coil's own network stack) + `org.json`, not Retrofit** | One GET endpoint doesn't justify a full Retrofit layer. In-memory cache keyed by `providerId`, *successes only* — a transient network failure is retried on the next focus rather than permanently disabling Tier 1 for that provider until the app restarts. |
| Settings screen hardware BACK key | **Explicit `BackHandler` on `Screen.Settings`, returning to `Screen.Launcher`** | Found on-device while testing Tier 1: since `MainActivity` hosts both screens as one Compose surface with no back-stack owner, the hardware/remote BACK key fell through to the Activity's default behavior (finish/move-to-back) and exited the entire launcher to whatever was previously foregrounded — the on-screen "Back" button worked correctly (it's just a state change), but the physical remote's back button did not, until this fix. |
| Tier 3 Channels query pattern | **Unfiltered query of `TvContract.Channels.CONTENT_URI` (no `selection`), filtered client-side by `COLUMN_PACKAGE_NAME`; programs queried via `TvContract.buildPreviewProgramsUriForChannel(id)`, not a raw `COLUMN_CHANNEL_ID` selection** | Confirmed on-device: `TvProvider` throws `SecurityException: Selection not allowed for content://android.media.tv/channel` on *any* selection against the Channels table — there's no supported "channels for package X" query. Programs, by contrast, accept a URI scoped to a known channel ID without issue. Framework `android.media.tv.TvContract` classes are used directly (no `androidx.tvprovider` dependency) — confirmed via `javap` against the real `android.jar` that this project's API 30 floor already has everything needed (available since API 26), and that `PreviewProgram`/`BasePreviewProgram` model/builder classes don't exist in the plain platform SDK at all (raw `Cursor` column access is used instead). |
| Tier 3 verification methodology | **Debug-only synthetic test channel (`app/src/debug/`'s `TestChannelSeederReceiver`, gitignored-equivalent via AGP's debug source set — never ships in release) to prove the query→UI pipeline, then final verification against real installed apps' own real data** | `TvContract` attributes every row's `package_name` to the actual calling app's UID — there's no way to spoof "Hulu published this." The debug seeder publishes under this app's own identity instead, letting the Content Rows UI (poster aspect ratios, missing-poster fallback, row header) be verified end-to-end before removing the temporary test hook and re-pointing the lookup at whichever app is really focused. This *also* surfaced the corrected "which apps publish channels" finding above — once queried correctly, Plex, Hulu, Jellyfin, Dolphin Emulator, and Apple TV were all found to already publish real channels on the reference device, letting the feature be verified against genuine production data (Hulu's and Jellyfin's real channels), not just the synthetic one. |
| `READ_TV_LISTINGS` grant for testing | **`adb shell pm grant <pkg> android.permission.READ_TV_LISTINGS`** | This is a special/runtime-style permission (declaring it in the manifest alone does not grant it — confirmed via `dumpsys package`, which showed it requested but not granted until explicitly granted). The settings screen's existing "Open app settings" CTA remains the real end-user grant path (§4); ADB grant was only used to unblock on-device *development* testing without navigating that UI flow repeatedly. |
| Glass tray width/alignment | **Full-width, matching the grid's own `ScreenSafeAreaHorizontal` content padding — not a content-sized "snug" panel** | User-directed reversal of an earlier decision (originally: a handful of pinned tiles got a tightly-hugging, centered panel). Tile columns now line up vertically between the tray and every grid row beneath it (tvOS photo reference, `design/IMG_1858.jpeg`), which a snug/narrower panel with its own `TrayPaddingHorizontal` inset couldn't guarantee. |
| Tray tile focus label | **Tray tiles render no per-tile focus label at all (`AppTile(showFocusLabel = false)`), grid tiles unchanged** | User-directed: the tray's own scale/glow focus motion already reads as "focused here" without a caption; §1.4's label stays grid-only. `TopShelfTrayHeight` reverted to tile-height-only (no reserved label space) to match. |
| Hero/tray collapse-on-grid-focus | **`LauncherScreen` animates `heroHeight` between two endpoints via `animateFloatAsState` on an "is focus in the tray" boolean**: expanded (tray focused — hero fills the screen minus a small grid-row-1 peek) and collapsed (grid focused — hero shrinks to exactly `TopShelfTrayHeight`, sitting flush at the very top, backdrop faded to transparent) | User-directed, tvOS photo reference (`design/IMG_1858.jpeg` — grid fully visible, no hero — vs `IMG_1859.jpeg` — hero dominant, only the next row's tile-tops peeking through). The tray itself never resizes; it's always bottom-aligned within the animating hero `Box`, which is what produces the "tray slides up" read as the hero collapses. `HeroGridPeekHeight` must clear `AppGrid`'s own top `contentPadding` (`ScreenSafeAreaVertical`) before any tile pixel is visible — confirmed on-device that an initial too-small value left the "peek" completely invisible (zero pixels, not a sliver). |
| Real glass-tray blur | **`GraphicsLayer.record`/`drawLayer` (Compose UI 1.7's real backdrop-capture API) + a `BlurEffect` `RenderEffect`, SDK-gated to API 31+; minSdk stays 30** | User asked for a real blur "since we're on API 31+," but the actual reference Shield TV Pro reports API 30 (Android 11) and cannot receive Android 12 — its final OS update ships that ceiling. Bumping `minSdk` to 31 would make the app permanently uninstallable on the one physical device this whole project has been built and tested against, so the blur is gated behind a `Build.VERSION.SDK_INT >= 31` check instead: `HeroBanner` records its own drawn content into a shared `GraphicsLayer` (owned by `LauncherScreen`), and `TopShelfRow` redraws that same layer again — blurred, translated by `heroHeight - TopShelfTrayHeight` so it lines up with whatever's actually behind the tray at that instant — behind its tiles. Below API 31, `backdropLayer` is `null` throughout and the tray falls back to the original translucent-tint-only look; this was the only path verified on-device this session (the reference Shield can't exercise the real-blur branch at all). **This entire mechanism was deleted** per the "Liquid glass removal — baked in permanently" entry below, then **a different mechanism rebuilt from scratch** much later per "Dock/pill backdrop blur" — not a revival of this one: the new version uses a downscale/upscale technique instead of `RenderEffect`, since this exact API-30-can't-do-`RenderEffect` problem is precisely why the new version isn't SDK-gated at all — it works on the actual reference hardware, which this original version never did. |
| Status bar clearance | **`LauncherScreen`'s content reserves `StatusBarClearance` (88dp) of top inset; the full-bleed background fill does not** — **reversed, see "Top-shelf/hero region extends to the true screen top edge" below** | Found on-device immediately after building the collapse behavior above: `StatusBar` is a separate overlay in `MainActivity`, positioned independently via `Alignment.TopEnd` — once the hero could collapse all the way to the screen's literal top edge, it visually collided with the clock/settings pill. `padding(top = StatusBarClearance)` is the last modifier in `LauncherScreen`'s chain, so it only shrinks what's available to content/children; the background color still reaches the true screen edge. |
| Glass tray outer margin | **`TrayOuterMargin` (32dp), applied as an outer margin around the whole panel (shadow/clip/background/border all sit inside it) — separate from the tray's inner content padding (`ScreenSafeAreaHorizontal`, unchanged, still what keeps tile columns aligned with the grid)** | User-directed refinement ("a little bit narrower") after the tray's full-width pass: the panel now reads as a floating card inset from the screen edge rather than a full-bleed bar, without touching where its tiles actually sit relative to the grid's columns. |
| Grid centering | **`AppGrid`'s `horizontalArrangement` is `Arrangement.spacedBy(TileSpacing, Alignment.CenterHorizontally)`, not plain `Arrangement.spacedBy(TileSpacing)`** | `GridCells.FixedSize` only computes *how many* columns fit at the given tile width — it doesn't center the resulting block, so any leftover width (column-count × tile-width not exactly filling the available space) sat as dead space on the right, reading as off-center. The centered-group overload fixes this without changing column count or tile size. |
| Content Rows label removed | **`ContentRows` no longer renders the channel's `displayName` as a header — the model field stays, just unrendered** | User-directed ("remove the label inside the hero section"). Found while resolving this: several installed apps' real channels were showing this header text (e.g. "BrowseHere Internet Browser," "Apple Original Shows and Movies") — removing it makes Content Rows read as pure media rather than media-plus-caption. **Reopened by §3.1.2's authoritative reference**, which specifies this header as a real element of the template this maps to (Template 3) — see §5's open question on this. **Superseded by "Multi-channel Content Rows" below** — the header is back, for a different reason (distinguishing simultaneous channels) than the one this entry removed it for. |

Not auto-reverted — see §5's reopened questions; these need an explicit decision, not a silent reversal. |

## 0. Non-Negotiable Performance Budget

Every decision in this document is subordinate to these numbers. If a feature can't fit the budget, it's cut or deferred.

| Metric | Budget | Rationale |
|---|---|---|
| D-pad input → visual focus response | ≤ 1 frame (≤ 8.3ms @ 120Hz, ≤ 16.6ms @ 60Hz) | tvOS-perceived instant response |
| Focus scale/tilt animation | 60/120 FPS, zero dropped frames during rapid traversal | Matches shelf's `UICollectionView` scroll feel |
| Cold launch → first frame | < 400ms | Shield boots to launcher; must feel instant on wake |
| App icon load on focus (cache hit) | 0 disk I/O, 0 decode — pre-composited `HARDWARE` bitmap blit only | Eliminates jank from bitmap decode on the UI/RenderThread |
| Jank (frames > 16.6ms) during grid scroll | < 0.5% of frames | Baseline Profile + AOT target |
| Memory footprint (idle, launcher foregrounded) | < 150MB | Leaves headroom for backgrounded TV apps on 3GB device |

## 1. Target UX & Physics Engine

### 1.1 tvOS Spring Dynamics

tvOS focus animations are not `ease-in-out` curves — they are physically simulated springs. We replicate this with Compose's `Animatable` + `spring()` AnimationSpec, **not** `tween()`. Tween-based easing is banned for focus-state transitions; it produces the "linear/robotic" feel that reads as non-native.

**Canonical spring parameters** (tuned to match tvOS's focus-engine feel, verified against 120Hz capture reference):

| Property | Stiffness | Damping Ratio | Notes |
|---|---|---|---|
| Scale (focus gain) | `Spring.StiffnessMedium` (~1500f) | `0.62f` (slightly under `DampingRatioMediumBouncy`) | Fast rise, one soft overshoot ≤2%, settles in ~220ms |
| Scale (focus loss) | `Spring.StiffnessMediumLow` (~400f) | `0.9f` (near `DampingRatioNoBouncy`) | No overshoot on release — snappy retreat, no wobble |
| Tilt (rotationX/Y) | `Spring.StiffnessHigh` (~3000f) | `0.75f` | Must resolve faster than scale so tilt never "lags" the scale-in |
| Elevation / shadow alpha | `Spring.StiffnessLow` (~200f) | `1.0f` (critically damped) | Shadow blur is expensive — animate cheaply, no bounce |
| Content translation (parallax layers) | `Spring.StiffnessMediumLow` | `0.8f` | Layer 2/3 parallax lags layer 1 by design (see 1.2) |

**Scale factors:**
- Unfocused (resting): `1.0x`
- Focused: `1.15x`, uniformly for both grid and top-shelf tiles — the original differentiated `1.08x`/`1.15x` split assumed top-shelf tiles were larger "hero cards"; since tiles are now the same size everywhere (§3.1), that reasoning no longer applies, and both use the grid's value.
- Pressed (D-pad center down, pre-launch): `1.08x` (brief compress-then-launch, 80ms hold before intent fires)

All spring specs are defined once as `@Immutable` `data class TvSpringSpec` constants in `ui/motion/TvSprings.kt` — never inlined at call sites, so the whole app can be re-tuned from one file.

### 1.2 Spatial Parallax / 3D Tilt

On focus gain, the focused card decomposes into up to 3 GPU layers (background art, mid content, foreground label/logo) rendered via nested `graphicsLayer` blocks — **not** separate composables re-measured per frame.

- `rotationX` / `rotationY` driven by D-pad *directional intent* at the moment of focus change (which direction did focus arrive from), clamped to **±6°** — tvOS itself stays subtle; anything past ~8° reads as gimmicky on a 10-foot display.
- `cameraDistance` increased (`8 * density`) to prevent perspective clipping/distortion at the 6° extremes.
- Parallax offset: background layer moves opposite to tilt direction at 0.3x magnitude, foreground layer moves with tilt at 1.0x — creates depth without any additional overdraw (same layer count, just offset math).
- **No continuous pointer/gyro tracking** — Shield TV has no pointer or motion sensor input in the target scenario. Tilt is a *discrete* focus-transition effect, not a continuous IMU-driven one. This matters: tilt animates from the incoming spring, then rests at 0° once settled — it is not persistently tilted.
- All tilt math happens in `graphicsLayer { }` lambda (deferred layer block), guaranteeing it executes on RenderThread, decoupled from the Compose UI thread's recomposition/layout pass. This is the single most important implementation detail for hitting the 1-frame input budget — see §2.3.

### 1.3 Spatial Focus Navigation

Deterministic, non-heuristic focus traversal — Android's default focus-search (geometric nearest-neighbor via `FocusFinder`) is **not trustworthy** at tvOS-grade reliability; it produces occasional wrong-neighbor jumps on irregular grids (e.g., top-shelf tray feeding into a regular grid below, even with same-size tiles on both sides of that boundary — §3.1).

- Section-level focus restoration ("returning to a row/section remembers its last-focused child") uses `Modifier.focusRestorer()` — verified during Phase 2 scaffolding against the actual `androidx.compose.foundation`/`androidx.compose.ui` API surface, not assumed. (Phase 1 draft of this spec named `Modifier.focusGroup()` for this; that API does not exist in the resolved library version and has been corrected here — see `README.md`'s note on this.)
- Explicit override of ambiguous edges via `Modifier.focusProperties { up = ...; down = ...; left = ...; right = ... }` at row-boundary tiles — specifically top-shelf ↔ grid transitions, and grid ↔ side-nav rail transitions, where geometric search is unreliable.
- A single app-wide `FocusManager` (domain-level, not a UI singleton) owns "last focused item per screen," restored via `FocusRequester.captureFocus()`/`requestFocus()` in `LaunchedEffect(Unit)` on screen composition — matches tvOS's "return to where you left off" behavior when backing out of an app.
- Initial focus on cold launch always lands on the top-shelf tray's first tile (index 0), never on the grid — matches tvOS home screen behavior.
- Focus search is exhaustively tested via a Robolectric/Compose UI test matrix asserting the exact next-focused-item for every (current position × D-pad direction) pair on the reference layout — this is a spec deliverable in Phase 2, not an afterthought.

### 1.4 Per-Tile Focus Label

**tvOS photo reference (`design/IMG_1858.jpeg`):** the focused icon (Prime Video, in that photo) grows a text caption directly *below the tile itself* — not in a separate hero/detail area elsewhere on screen. This replaces the name/tagline text originally planned for `HeroBanner` (see Decisions Log and §3.1.1) — that design was extracted from `hamtv`, a web project with no per-tile focus concept at all, and produces a redundant second copy of the app's name once every tile can label itself.

- Label text = the app's display name (`TvApp.label`), shown only while the tile is focused — appears and disappears with focus, not persistently visible.
- Reuses existing focus-transition timing rather than introducing new constants: fade in/out on the same `FocusGainMillis`/`FocusLossMillis` tween budget already used for the border ring and content-dim (§1.1's spring table covers scale/tilt/elevation; border/dim/label are plain crossfades tuned to match those settle times — see `ui/focus/TvFocusable.kt`'s existing fade constants).
- Positioned outside the tile's own bounds (below it, not overlaid on the artwork), so it needs layout space reserved beneath each tile — grid row spacing (`TileSpacing`) and the top-shelf tray's own padding need to account for this rather than the label clipping into the row below or the tray's edge.
- Typography: small, high-contrast, single line — this is a caption, not a heading; it should read as secondary to the tile's own art, matching the reference's proportions (the label is noticeably smaller than `HeroBanner`'s old name treatment was).
- **Resolved (Decisions Log: "Per-tile focus label reserved space")**: space is reserved *permanently* — every tile always composes its label at fixed height, only its alpha animates with focus. Built and confirmed on-device; also surfaced a related fix (same Decisions Log entry) around getting the reserved label area actually scrolled into view on focus, not just the tile itself.

## 2. System Architecture & Performance Strategy

### 2.1 System Integration — Home Launcher Registration

- Manifest declares the launcher `Activity` with intent-filter `action=MAIN`, `category=HOME`, `category=DEFAULT`, `category=LEANBACK_LAUNCHER` (the TV-specific category Android TV's home-picker and Play Store leanback validation both key off of).
- **No accessibility service, no overlay window, no `SYSTEM_ALERT_WINDOW`.** This is a true launcher replacement (`Intent.ACTION_MAIN` / `Intent.CATEGORY_HOME` resolution), not an overlay hack — overlays cannot achieve frame-perfect input latency because they sit in a separate window layer subject to WM compositing overhead and cannot own the D-pad input focus root.
- `android:launchMode="singleTask"`, always resident (`android:excludeFromRecents="true"` is *not* set — launcher must remain a normal, killable/restorable task per TV OS conventions) with process priority naturally elevated by the system while foregrounded as HOME.
- Required manifest hardware feature declarations: `android.software.leanback` (required="true"), `android.hardware.touchscreen` (required="false" — critical, its absence/false is what makes the app installable/visible as a TV launcher at all).
- Home-button (`KEYCODE_HOME`) long-press and double-tap are *not* intercepted — standard TV OS behavior (recents, app-switch) must keep working; the launcher only owns the "resting" home surface.

### 2.2 Hardware-Accelerated Asset Pipeline

Goal: **zero decode cost on the critical input→focus path.** Icon/artwork decode must never happen synchronously as a result of a focus event.

- **Coil** `ImageLoader` configured with:
  - `bitmapConfig = Bitmap.Config.HARDWARE` for all displayed icons/artwork — bitmap lives in GPU-accessible graphic memory, immune to CPU-side decode-on-focus stalls, and immutable (read-only) which matches our use case exactly.
  - A dedicated `MemoryCache` sized via `MemoryCache.Builder().maxSizePercent(context, 0.25)` — generous, since the whole app-icon set for a Shield's installed-app count (~40-150 apps) is small relative to available RAM.
  - Disk cache **pre-warmed at app-install-broadcast time** (see 3.2), not lazily on first scroll — so first-ever grid render already hits memory cache, not network/disk.
- **Pre-composition, not pre-fetch alone:** icons are decoded to `HARDWARE` bitmaps and held in the in-memory `LauncherAppRepository` cache as part of the app-list build step (triggered on boot + package-change broadcasts), *before* the grid ever composes. The grid's `AsyncImage`/`rememberAsyncImagePainter` calls should always resolve from the warm memory cache; a disk/network fetch on the focus path is treated as a bug, not a fallback path.
- Icons sourced via `PackageManager.getApplicationBanner()` (TV banner, preferred — 320×180 leanback banner asset) falling back to `getApplicationIcon()` only when a TV app declares no banner; banner-vs-icon aspect ratio is normalized at decode time so grid layout math never branches on asset shape at composition time.
- `graphicsLayer(compositingStrategy = CompositingStrategy.Offscreen)` used selectively only on the actively-focused card (for the tilt/parallax layer composition in §1.2) — **not** applied blanket across the grid, since offscreen compositing has a real GPU cost and 100+ simultaneous offscreen layers would blow the frame budget.

### 2.3 Frame Pacing & Compilation

- **Baseline Profiles** generated via the `androidx.benchmark.macro` `BaselineProfileRule`, covering the critical user journeys: cold start → top-shelf render, D-pad traversal across the full grid (up/down/left/right sweep), and app-launch transition. Profile is checked into `app/src/main/generated/baselineProfiles/` and packaged via the Baseline Profile Gradle plugin (`androidx.baselineprofile`), forcing these code paths through ART's AOT/dex2oat compilation on install rather than falling back to JIT-interpreted execution on first run.
- `R8` full mode + resource shrinking enabled for release builds; the focus-modifier and spring-spec code paths are added to a `keep` allowlist verification test (a shrunk build that inlines away the spring math would silently regress motion quality without a functional test catching it).
- **RenderThread isolation is the core latency strategy**: all focus-reactive visual mutation (scale, rotation, alpha, translation) is expressed via `graphicsLayer { }`'s deferred lambda form, which Compose executes on RenderThread independent of the UI thread's recomposition/layout/draw passes. This means a focus change *never* requires the UI thread to be free — even if the UI thread is momentarily busy (e.g., a package-manager query on a background-adjacent frame), the spring-driven visual response still lands on time. This is the mechanism, not a hope, behind the ≤1-frame budget in §0.
- `Modifier.focusable(interactionSource = ...)` focus-state reads are hoisted to drive `Animatable` targets via `snapshotFlow`, never read inside `Modifier.graphicsLayer`'s own block in a way that forces a full recomposition per animation tick — animation ticks must only invalidate the draw phase, never layout/measure.
- Target explicitly supports both 60Hz and 120Hz display output; spring specs are expressed in physical units (stiffness/damping), not frame counts, so they self-adapt to the Shield's refresh rate without separate 60/120 tuning tables.
- `StrictMode` (disk/network-on-main-thread penalties) enabled in debug builds specifically to catch any accidental icon-decode-on-focus-path regression before it ships.

### 2.4 Content Channel Integration (Home Screen Channels)

**tvOS photo reference (`design/IMG_1859.jpeg`):** the real tvOS home screen shows portrait poster-style content rows ("Continue Watching," "Recently Released Movies on ...") above the icon dock — but only for apps that supply that content; this is Apple's "Top Shelf" mechanism. Android TV's direct equivalent is the **Home Screen Channels API**: a `ContentProvider`-based system (`TvContractCompat`, tables `Channels` and `PreviewPrograms`) that apps opt into publishing content through.

- **Reading *other apps'* channels from a third-party, non-default-Home launcher is confirmed feasible**, not just theoretically possible — this was an open research question this pass resolved. The mechanism is the `android.permission.READ_TV_LISTINGS` permission, which is a user-grantable *special permission* (surfaced via a Settings toggle, similar to Accessibility or notification access) rather than a simple runtime dialog, a signature permission, or something requiring the app to hold the Home role.
- **Working precedent, on the actual target hardware**: Projectivy Launcher — already installed on the reference Shield TV Pro unit used for this project's on-device testing — requests exactly this permission and successfully surfaces Prime Video/Apple TV+/Disney+ channel rows as a sideloaded, non-default launcher. This is not a hypothetical architecture; it's independently confirmed working on the same device class this spec targets.
- **On-device finding that reopened the "supersedes TMDB" call above** (§5 open question #4): `adb shell content query` against `content://android.media.tv/{channel,preview_program,watch_next_program}` on the actual target Shield returned **zero rows across every currently-installed app** — `com.android.providers.tv/.TvProvider` is confirmed registered and reachable (a real empty result, not a permission error), but nothing installed here (Hulu, Jellyfin, Plex, Apple TV, etc.) currently publishes to it. This doesn't invalidate the mechanism — it's real and working, per the Projectivy precedent below — but it means Channels can't be the *primary* content source in practice today, only an opportunistic one.
- **Three-tier hybrid model this now feeds** (see §3.1.1's "Content Rows / `ContentCarousel`" subsection and the revised Decisions Log entry): **Tier 3** (this section, highest display priority when present) — an app with real published channel data gets a full-screen carousel of its own content when focused (`ContentCarousel`, Decisions Log: "Full-screen Content Rows carousel"), superseding everything else for that app. **Tier 1** — curated apps (§3.2.1's `tmdb_provider_id`, restored to active use, not legacy) get TMDB-sourced backdrop art in the hero when Tier 3 isn't available. **Tier 2** — everything else falls back to the existing static system-banner treatment. TMDB is *not* superseded after all; it's Tier 1, sitting between real Channels data and the plain banner fallback, precisely because Channels data is currently the exception, not the rule, on the actual hardware.
- **Query mechanism**: background `ContentResolver.query()` against `TvContractCompat.Channels.CONTENT_URI` (to discover which installed packages have published a channel, and that channel's display name — which becomes the row header, resolving §3.1.1's "row labels" question) and `TvContractCompat.PreviewPrograms.CONTENT_URI` (per-channel program/poster data) — read-only from this launcher's perspective; we never write channels of our own.
- **Permission request UX**: since `READ_TV_LISTINGS` requires a Settings-toggle grant rather than a runtime dialog, the launcher needs a deep-link/CTA into that settings screen — this is one of the two concrete drivers (with the theme toggle) for walking back §4's original "no settings screen" non-goal.
- **Play Store policy note** (relevant if this ever ships beyond sideloading): broad `READ_TV_LISTINGS` usage is generally restricted to apps that are genuinely acting as a TV launcher — which this app is, so this should be compliant, but worth confirming against current policy text before a real release, not assumed.

## 3. Core Feature Set

### 3.1 Minimalist tvOS Grid Layout

- **Top-shelf tray**: a horizontally-scrollable panel (**translucent fill over a blurred crop of whatever's behind it — hairline border/drop shadow stay removed. The Decisions Log's "§3.1.1 'liquid glass' tray/pill styling — removed" entry took this fully opaque; "Dock/pill backdrop blur" reopened translucency + blur specifically for the tray and the status pill, not the border/shadow it removed alongside them — see that entry for the mechanism**) holding pinned/priority apps, rendered above the fold, always the first focus target on cold launch. **Tiles here are the same size as the grid's** — confirmed against the actual `hamtv` reference (its `.tile-row-glass` uses the identical tile size as its main grid); an earlier pass in this project made top-shelf tiles deliberately larger ("hero cards"), which was a mistake corrected during Phase 2 on-device testing, not the current design.
- **App grid**: below top-shelf, a uniform grid (`androidx.compose.foundation.lazy.grid.LazyVerticalGrid` with `GridCells.FixedSize`, not `Fixed(N)`/`Adaptive` — both stretch cells to fill available space, confirmed on-device; not a TV-specific composable either) of all installed leanback apps, sized to fit 5–6 columns at 1080p/4K TV scale per the actual measured screen width, not a hardcoded column count.
- No persistent chrome/nav chatter — background is a subtly animated/parallaxing gradient or blurred-dominant-color wash derived from the focused item's artwork (cheap: sampled at decode time, not per-frame blur), echoing tvOS's ambient background behavior without a real-time blur compositing cost.
- Row/section labels are minimal, low-emphasis typography — content art carries the visual weight, exactly as tvOS treats it.

**Hero content structure (within the banner) — revised after §1.4/§2.4's decisions:**

- **Superseded from the original extraction**: the "hero card" (logo + name + tagline + subtitle text block) and the "prev/next content nav pills" described below are **no longer part of the plan**. The name/tagline text is now the per-tile focus label (§1.4) instead of a separate hero text block — `hamtv`'s design had no per-tile focus concept, so it put that text in the hero; tvOS puts it on the tile, and now so do we. The prev/next nav pills existed to page through TMDB-rotated content, which no longer applies (see below).
- What remains: Backdrop image layer → **vignette overlay** (bottom + left edges fade to background color, for legibility) → **clock pill** (top-right corner, always visible — see §2.4-adjacent status bar note; this is confirmed as an actual Phase 3 build item, not just an extracted-but-unbuilt reference detail).
- Backdrop treatment: `brightness(0.65)` darken filter over the raw artwork, slight `scale(1.02)` overscan to avoid edge seams during crossfade — both are cheap, decode-time-safe techniques worth porting as *effects* (implement via `ColorFilter`/`graphicsLayer.scaleX/Y` in Compose, not CSS `filter`).
- **Three-tier content model** (§2.4, revised Decisions Log — reopened from an earlier "Channels supersedes TMDB" call in this same session, initially over an incorrect "zero apps publish channel data" reading that Task #20's implementation later corrected — see Decisions Log): **Tier 3** — an app with a published Home Screen Channel gets the hero region replaced entirely by that channel's content (see "Content Rows" below), highest display priority whenever it's actually present. **Tier 1** — a curated app (§3.2.1's `tmdb_provider_id`, active again, not legacy) without Tier 3 data gets a TMDB-sourced backdrop in the hero — *art only*, no name/tagline text (that stays the per-tile focus label, §1.4 — not reopened). **Tier 2** — everything else gets the **static, non-rotating backdrop** already built (the app's own banner/logo art, darkened per above). Tier 2 was the *only* fallback tier as originally speced this session; it's now specifically the bottom of three, not the sole alternative to Tier 3.
- Tier 1's backdrop **may rotate** through TMDB's trending/featured list for that app every 5–10s, reviving the original "content rotation" bullet this section briefly dropped earlier this session (when TMDB was thought superseded) — since only the *art* rotates now (no text stack to stagger/reveal per-element), this is simpler than the original `hamtv`-derived plan: a plain crossfade between backdrop images, still governed by the darkening/overscan treatment above, still lower-priority than and never competing with the D-pad focus-response path (§2.3).

**Content Rows / `ContentCarousel` (Home Screen Channels, Tier 3) — see §2.4:**

**Superseded from the original extraction and the Phase 3 build that followed it**: the horizontally-scrolling *row* of small posters described in earlier drafts of this section (`ContentRows`, mapping to §3.1.2's Template 3) was built, then deleted outright and replaced by `ContentCarousel` — a full-screen, auto-advancing carousel mapping to §3.1.2's **Template 1** instead (Decisions Log: "Full-screen Content Rows carousel"). Real tvOS's actual Top Shelf for an app like Apple TV or Hulu is this template, not Template 3 — user-directed, after the row treatment read as small, static, and non-selectable against the real reference.

- One program at a time, full-bleed, from the focused app's *primary* (first) channel only — `AppChannel.programs`, aspect-ratio-scaled via `Crop` (not the per-program aspect ratio `ContentRows` preserved; a full-screen backdrop crops to fill regardless of the source poster's own shape, same treatment `HeroBanner` already gives Tier 1/2 art).
- Auto-advances every 5s (`PosterHoldMillis`), `Crossfade`-transitioned; after the hold, crossfades into playing that program's trailer if `COLUMN_PREVIEW_VIDEO_URI` is published (Decisions Log: "Trailer playback... confirmed currently inert" — the mechanism is real, but no installed app on the reference device populates this column today) until it ends or errors, then advances. D-pad Left/Right manually retreat/advance at any point, resetting the cycle; Center/Enter launches the current program (`onProgramClick` → `AppLauncher.launchContent`, same mechanism `ContentRows` used).
- **Only the primary channel renders** — a real trade-off, not an oversight: a full-screen carousel is inherently one-at-a-time, so "Multi-channel Content Rows"' simultaneous stacked-sections display (multiple channels, each its own row + header) doesn't carry over into this presentation. The underlying `ChannelsRepository.fetchChannels()` fix (surfacing every channel a package publishes, not just the first found) is still in effect — `ContentCarousel` just consumes `tier3Channels.firstOrNull()` from that same list, rather than rendering all of them simultaneously.
- No channel-name header — Template 1 has no such element (that was specifically Template 3's), and there's no "distinguishing between simultaneous channels" need anymore now that only one ever shows.
- No API key, no provider-ID mapping table to maintain **for this tier specifically** — content is whatever the app itself chose to publish, inherently accurate (never mismatched trending content from an unrelated source). Tier 1, by contrast, does need both (§3.2.1/§3.3.1) — that trade-off (curated-but-approximate vs. real-but-rare) is exactly why this is a three-tier fallback rather than a single mechanism.

**Ambient background (`bg-glow` in the reference):**

- A large, heavily blurred, low-opacity color wash tied to the focused item's accent color, positioned behind all content, that smoothly re-tints (not re-positions) when focus changes.
- **Decided technique (see Decisions Log)**: the web version uses a true CSS Gaussian blur (`filter: blur(120px)`), which has no RenderThread-cheap equivalent on the confirmed API 30 floor (`RenderEffect` hardware blur requires API 31+). Implement instead as a **dual-stop radial gradient** (`Brush.radialGradient`, two color stops fading from `accentColor` at partial opacity to transparent), full-bleed behind all content, drawn once per focus change rather than per frame — no blur filter, no offscreen compositing pass. This reproduces the "room lighting shift" read without a blur compositing cost.
- Color/position re-tint on focus change should be a smooth animated color interpolation (`animateColorAsState` or a spring-driven color animation), not an instant swap — deliberately slower/softer than the focus-scale spring in §1.1.

**Grid tile reference dimensions:**

- Reference tile: 200×130px (≈1.54:1 aspect ratio), 14px corner radius, 22px gap between tiles, 1px hairline border.
- **Decided (see Decisions Log)**: native grid tiles standardize on **16:9 (1.78:1)**, matching the 320×180 leanback banner sourced directly via `PackageManager.getApplicationBanner()` (§2.2) — not the reference's 1.54:1. This avoids dynamic cropping/letterboxing on every system-supplied third-party banner. Corner radius, gap, and border-weight proportions from the reference still carry over; only the tile's aspect ratio changes. Curated apps (§3.2.1) that need different framing use the enrichment schema's `logoFit`/`logoPadding` overrides (e.g., `ContentScale.Fit` with padding) rather than a different tile shape.
- Tile background is a solid fill of the app's per-app accent color (falls back to a neutral dark gray when unset) — logo art sits on top.
- **Artwork treatment — revised after the tvOS photo reference (`design/`)**: default is `ContentScale.Crop` (built during Phase 2 after discovering it's the only mode that guarantees no letterbox gap regardless of a source banner's actual aspect ratio — see the on-device dim-artifact fix this pass's predecessor made). The tvOS photos show every real icon as a *compact, centered logo/wordmark on a flat card with generous padding*, which `Crop` alone can't produce — it fills the tile, it doesn't frame a mark within it. Per the Decisions Log: `Crop` stays the **generic fallback** for arbitrary system banners we have no curated art for; known/curated apps (§3.2.1) should get `ContentScale.Fit` + `logoPadding` + a solid `accentColor` background instead, deliberately reproducing that flat-card-with-centered-mark look. This makes building out §3.2.1's enrichment data source (currently speced but not implemented) a real priority, not a nice-to-have — it's the only path to matching the reference for the apps that matter most.
- No-logo / load-failure fallback: a centered, single uppercase initial letter on a muted neutral background — this is the tile-level fallback (already built in `AppTile.kt`). There is no separate hero-level fallback treatment anymore (§1.4 removed the hero's logo/text badge entirely); the tile's own fallback plus its focus label (§1.4) is the complete treatment now.
- Focus state (visual target, not the transition mechanics — those stay governed by §1): a bright hairline ring plus a soft glow shadow tinted with the app's accent color at partial opacity, plus the focus label below the tile (§1.4). This confirms the accent-color system should drive the focus glow color, not just a fixed white/neutral highlight.

#### 3.1.2 Authoritative Reference — Apple's Official Top Shelf Template System

Superseding source for hero/Top Shelf behavior — more authoritative than the `hamtv` web reference (§3.1.1) or the two tvOS photos (`design/`) alone, both of which this project had been reverse-engineering assumptions from. Apple calls this region the **Top Shelf**; whichever dock app currently holds D-pad focus populates it via one of four system templates. This section doesn't replace §2.4/§3.1.1's three-tier *content-sourcing* model (Tier 1/2/3 still determine which data feeds the hero) — it's the authoritative description of what each tier's *presentation* should actually contain, which turned out to be considerably richer than what's built.

**Template 1 — Full-Screen Carousel (Details/Actions).** Full-bleed backdrop art (or an auto-playing preview — reopened, §4), a vignette along the bottom **and left** edges, a title/logo treatment lower-left, a metadata stack (tagline, content rating/release year/runtime/genre, episode/season badge), and two focusable action buttons (primary: Play/Resume; secondary: More Info). **This is now what Tier 3 maps to** (`ContentCarousel`, Decisions Log: "Full-screen Content Rows carousel") — reassigned from Template 3 below, which this project built first, then moved away from.

**Template 2 — Inset/Banner Carousel.** Large raised cards using Apple's layered-parallax (`.lsr`) image format, plus carousel pagination indicators. One of several templates a real app can opt into — not mandatory for every app, and not attempted here (see §4).

**Template 3 — Sectioned Content Rows.** A low-contrast section header, a horizontal scrollable poster row, and — critically — **the row itself is focusable**: moving D-pad focus into it scales/lifts the selected poster and reveals a title/subtitle beneath it. **No longer what Tier 3 maps to** — this was built (as `ContentRows`), then deleted and replaced by a Template 1 mapping instead (Decisions Log: "Full-screen Content Rows carousel"); kept here only as the reference description of a template this project tried and moved away from.

**Template 4 — Static Fallback.** A blurred, mirrored, full-width copy of the app's own banner art, with the app's logo centered over that blur. This is what our Tier 2 should be doing.

### 3.2 App Management Engine

- `LauncherAppRepository` (domain-facing interface, `data/` impl) queries installed apps via `PackageManager.queryIntentActivities(Intent(Intent.ACTION_MAIN).addCategory(Intent.CATEGORY_LEANBACK_LAUNCHER), ...)` — the TV-specific launcher category, not the phone/tablet `CATEGORY_LAUNCHER`, so non-TV-optimized apps that happen to be installed don't clutter the grid.
- Dynamic updates via a registered `BroadcastReceiver` for `ACTION_PACKAGE_ADDED`, `ACTION_PACKAGE_REMOVED`, `ACTION_PACKAGE_REPLACED` (manifest-registered is insufficient on modern Android for implicit broadcasts — registered at runtime in a long-lived scope tied to the launcher process/Application, since the launcher *is* the always-resident process).
- App list changes flow through a single `StateFlow<List<TvApp>>` domain model consumed by the grid — additions/removals animate in/out via Compose's `AnimatedVisibility`/`Modifier.animateItemPlacement()`-equivalent (`animateItem()` in current TV grid APIs) rather than a hard reflow, so a background install doesn't visually jar a user mid-navigation.
- Package query + icon pre-composition (§2.2) is debounced/coalesced when multiple broadcasts arrive in a burst (e.g., a batch of updates after a Shield reboot).

#### 3.2.1 Curated Metadata Enrichment Schema

`PackageManager` (§3.2 above) remains the **sole source of truth** for *which apps exist* — this schema does not replace it. It's a supplementary, package-name-keyed enrichment layer (local JSON or Room table, bundled + user-editable) that supplies presentation data `PackageManager` doesn't have: accent color, asset overrides, and TMDB provider linkage. It is directly modeled on `../hamtv/config.json`'s tile schema, field-mapped to native purposes. **Building this out is now a real priority** (§3.1.1's icon-artwork guidance and Tier 1 hero backdrops both depend on it), not just a speced-but-unbuilt schema:

| Web field (`config.json`) | Native `LauncherAppRepository` equivalent | Notes |
|---|---|---|
| `name` | Display-name override | Optional — `PackageManager`'s app label is the default; only needed when a friendlier name is desired |
| `url` | *Dropped for installed apps* | Native launch uses `getLeanbackLaunchIntentForPackage()` (§3.3), not a URL. Retained only for the "not installed" fallback case (§3.3.1) — a web/store link to offer instead of a broken launch |
| `logo` | Banner/icon override path | Used only when the pipeline in §2.2 needs a better asset than the app's own leanback banner (e.g., a sideloaded app with no banner, or a curated flat-card logo per §3.1.1's icon-artwork decision) — same `HARDWARE`-bitmap Coil pipeline, different source |
| `color` | `accentColor: Color` | Drives the focus-glow tint (§3.1.1) and the ambient background wash (§3.1.1) — the hero fallback badge this used to also feed no longer exists (§1.4 removed the hero's logo/text badge) |
| `newTab` | *Dropped* | Web-only concept (open in new browser tab); native task-stack behavior is already fully specified in §3.3 |
| `tmdb_provider_id` | `tmdbProviderId: Int?` — **active, Tier 1** | Powers Tier 1 hero backdrop art (§3.1.1's three-tier model) for curated apps without real Channels data (§2.4) — that's most curated apps still, since Tier 1's own curated list (Apple TV, Peacock, Paramount+, Prime Video, YouTube) is largely disjoint from the apps Task #20 found actually publishing Channels (Plex, Hulu, Jellyfin, Dolphin Emulator) on the reference device, aside from Apple TV/Hulu overlapping both lists (Tier 3 wins for those two whenever their real channel is present). |
| `inTray` | `pinnedToTopShelf: Boolean` | Determines whether an app renders in the top-shelf row vs. the general grid — absence of the field defaults to `false`, matching the reference's behavior |
| `logoFit` | `ContentScale` mapping | `fill-v`→`FillHeight`, `fill-h`→`FillWidth`, absent/`contain`→`Fit` — `Fit` is the mode to use for curated flat-card logo treatments per §3.1.1, vs. `Crop`'s generic-fallback default |
| `logoPadding` | `Dp` inner padding | Per-app override for asset-specific inner padding — for curated apps (§3.1.1), this is what actually produces the "generous padding around a centered mark" look the tvOS photo reference shows |

This enrichment data should be optional per app — an installed app with no matching entry still renders correctly with `PackageManager`-sourced defaults (system icon, no accent, Tier 2 static hero backdrop, general-grid placement). The schema exists to enhance known/curated apps, not to gate what appears in the launcher.

### 3.3 Deep-Link Launcher Support

- Apps are launched via their registered `LEANBACK_LAUNCHER` intent (`PackageManager.getLeanbackLaunchIntentForPackage()`), which is the TV-correct equivalent of `getLaunchIntentForPackage()`.
- Launch `Intent` flags: `FLAG_ACTIVITY_NEW_TASK` only when no existing task exists for the target package; if a task already exists (app was merely backgrounded), we bring it forward via `ActivityManager`/`ActivityTaskManager` task-move semantics rather than re-launching — avoids duplicate task-stack entries ("task stack pollution") and matches tvOS's single-instance-per-app model.
- Launch is fired only after the press-compress animation's intent-fire delay (§1.1, 80ms) — matches tvOS's tactile "commit" feel and avoids accidental double-launch from a fast double-press.
- No launcher-owned back-stack manipulation of the *target* app's internal navigation — once launched, the launcher's job is done until the user returns via `KEYCODE_HOME` or the app finishes.
